# قرارداد بستهٔ CSV برای ممیزی ۲۷۰ رویداد

> این قرارداد بین DBA (تولیدکننده) و هارنس داوری (مصرف‌کننده) است. هر تغییری در ستون‌ها باید هم‌زمان در `export_other_270.sql` و `adjudicate.REQUIRED_COLUMNS` اعمال شود، وگرنه `build` بسته را رد می‌کند.

## ۱. فایل‌ها، ستون‌ها و کلیدها

CSV با سرصفحه، کدگذاری UTF-8، جداکنندهٔ ویرگول (`FORMAT csv, HEADER true`). `\copy` فیلدهای دارای ویرگول/نقل‌قول/خط جدید را درست quote می‌کند.

### `events.csv`
| ستون | نوع | الزامی | معنا |
|---|---|---|---|
| `id` | bigint | ✓ | **کلید اصلی** |
| `title` | text | ✓ | عنوان رویداد |
| `event_type` | text | ✓ | نوع رویداد (می‌تواند خالی باشد) |
| `countries` | jsonb به‌صورت متن | ✓ | آرایهٔ کشورها |
| `actors` | jsonb به‌صورت متن | ✓ | آرایهٔ بازیگران |
| `location` | text | ✓ | مکان (می‌تواند خالی باشد) |
| `importance` | smallint | ✓ | اهمیت |
| `status` | text | ✓ | وضعیت رویداد |
| `first_seen_at` | timestamptz | ✓ | اولین مشاهده |

### `articles.csv`
| ستون | نوع | الزامی | معنا |
|---|---|---|---|
| `id` | bigint | ✓ | **کلید اصلی** |
| `title` | text | ✓ | عنوان مقاله |
| `source_name` | text | ✓ | نام منبع؛ برای مقالهٔ بدون منبع **خالی** می‌ماند (مقاله حذف نمی‌شود) |
| `original_url` | text | ✓ | نشانی اصلی |
| `published_at` | timestamptz | ✓ | زمان انتشار |
| `collected_at` | timestamptz | ✓ | زمان جمع‌آوری؛ مبنای پنجره |
| `status` | text | ✓ | وضعیت پردازش مقاله |
| `original_text` | text | ✓ | **متن کامل، بدون truncate** |

### `article_events.csv`
| ستون | نوع | الزامی | معنا |
|---|---|---|---|
| `article_id` | bigint | ✓ | کلید خارجی به `articles.id` |
| `event_id` | bigint | ✓ | کلید خارجی به `events.id` |

کلید ترکیبی طبیعی: `(article_id, event_id)`.

### `summaries.csv`
| ستون | نوع | الزامی | معنا |
|---|---|---|---|
| `event_id` | bigint | ✓ | کلید خارجی به `events.id` |
| `headline_fa` | text | ✓ | تیتر فارسی |
| `verification_status` | text | ✓ | وضعیت راستی‌آزمایی |
| `model_name` | text | ✓ | مدل تولیدکننده |

> اگر برای یک رویداد چند خلاصه وجود داشته باشد، شیت کور اولین خلاصه را نشان می‌دهد؛ این حذف شاهد مقاله نیست و در `meta.json` شمارش خلاصه‌ها ثبت می‌شود.

## ۲. تعداد مورد انتظار

| فایل | انتظار |
|---|---|
| `events.csv` | تعداد رویدادهای یکتایی که حداقل یک مقاله با `collected_at` در پنجره دارند |
| `articles.csv` | **همهٔ** مقالات پنجره (شامل مقالات بدون رویداد و بدون منبع) |
| `article_events.csv` | همهٔ نگاشت‌های مقالات پنجره |
| `summaries.csv` | خلاصه‌های همان رویدادها (می‌تواند صفر باشد) |

برای گزارش مرجع این مرحله، انتظار مستند: ۳۴۸ مقاله در پنجره و ۲۷۰ رویداد در «سایر تحولات». این اعداد **معیار موفقیت نیستند**؛ عدد قطعی باید از بلوک ۰ب همان اجرا بیاید و در `meta.json` ثبت شود. اختلاف باید توضیح داده شود، نه اصلاح.

## ۳. قواعد یکپارچگی که `build` اعمال می‌کند

1. هر چهار فایل موجود باشند و همهٔ ستون‌های الزامی را داشته باشند.
2. `events.id` و `articles.id` یکتا باشند.
3. هر سطر `article_events` به مقاله و رویداد موجود اشاره کند (بدون لینک معلق).
4. هیچ مقاله‌ای به‌خاطر نبود منبع، نبود رویداد یا نبود خلاصه حذف نشود.

نقض هر کدام ⇒ `ValueError` و توقف پیش از ساخت شیت کور.

## ۴. آنچه نباید در بسته باشد

- خروجی `match_topics` یا هر برچسب موضوع.
- `event_type` به‌عنوان جایگزین برچسب کافی نیست، اما چون خودش بخشی از تحلیل است، حفظ می‌شود و در داوری فقط شاهد است.
- رمز، DSN، یا مسیر فایل کلید.

## ۵. بازتولید

`meta.json` شامل `input_hashes` هر چهار فایل و `data_checks` (تعداد ردیف‌ها، صفر لینک معلق) است. با همان بسته و همان نسخهٔ کد، شیت کور باید بایت‌به‌بایت بازتولید شود.
